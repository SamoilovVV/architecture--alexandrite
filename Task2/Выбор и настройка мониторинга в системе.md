# Выбор и настройка мониторинга в системе

## Мотивация
В настоящий момент система подвержена ряду проблем, самая серьёзная из которых состоит в том, что заказы "зависают" внутри системы, что приводит к значительным задержкам исполнения заказов и напрямую влияет на бизнес-показатели компании и удовлетворённость клиентов.
При этом причины проблем и узкие места системы достоверно неизвестны, поэтому предположения специалистов компании и способы решения далеко не всегда приводят к результатам (см. внедрение пагинации и фильтра по статусам для решения проблемы медленной загрузки страницы).

Внедрение мониторинга поможет:
- выявить узкие места в цепочке обработки заказов
- снизить время диагностики проблем
- повысить оперативность обнаружения сбоев

Таким образом, после внедрения системы мониторинга станут очевидны узкие места и причины возникновения рядя ошибок, что, в свою очередь, позволит техническим специалистам компании предлагать обоснованные и эффективные решения проблем.

## Выбор подхода к мониторингу
Предлагается использовать комбинированный подход к мониторингу:
- Для API-сервисов предлагается использовать метод "четырёх золотых сигналов", т.к. для API нам важны задержки, количество запросов, ошибки и насыщенность
- для RabbitMQ, баз данных и S3-based storage выбираем метод USE, т.к. для данных частей системы критична производительность и есть предположения, что она серьёзно проседает при увеличении нагрузки.

### Метрики для отслеживания

#### CRM API / MES API / shop API
1. **Number of requests (RPS)** (for CRM API / MES API / shop API) — частота запросов позволяет определить активность пользователей и соответственно нагрузку сервиса. Отслеживание трафика поможет спрогнозировать потребность в увеличении ресурсов при дальнейшем росте трафика.

2. **Response time (latency)** (for CRM API / MES API / shop API) — время выполнения одного запроса. Позволят определить скорость работы и "отзывчивость" системы. 

3. **Number of HTTP 500** (for CRM API / MES API / shop API) — количество неудачных запросов в секунду. Резкое повышение данного показателя может быть признаком проблем с инфраструктурой и/или недостатка ресурсов.

4. **CPU %** (for CRM API / MES API / shop API) — среднее время, когда ресурс занят работой. Рост данного показателя выше 70-80% показывает нехватку вычислительной мощности и необходимость оптимизации или масштабирования.
	
5. **Memory Utilisation** (for CRM API / MES API / shop API) — процент использования оперативной памяти. Рост данного показателя выше 70-80% показывает нехватку оперативной памяти и необходимость оптимизации или масштабирования.

#### RabbitMQ:
1. **Number of dead-letter-exchange letters in RabbitMQ** — показатель количества "плохих" сообщений. Рост данного показателя может указать на возможный источник проблем с "зависшими" заказами.
2. **Number of message in flight in RabbitMQ** — показатель количества сообщений в очереди. Рост количества сообщений выше определённого порога может свидетельствовать о необходимости горизонтального масштабирования.

### Базы данных (Shop DB, MES DB)

1. **Memory Utilisation** (for shop db / MES db) — процент использования оперативной памяти. Рост данного показателя выше 70-80% показывает нехватку оперативной памяти и необходимость оптимизации или масштабирования.

2. **Number of connections** (for Shop DB / MES DB) — количество одновременных соединений. Если показатель стабильно растёт, то необходимо оптимизировать или масштабировать БД.
	
#### S3-based Storage

1. **Size of S3 storage** — размер S3-based хранилища. Рост объёма хранилища может потребовать масштабирования или изменения политики хранения файлов (автоудаление через N дней)


## План действий
1. Развернуть и сконфигурировать Prometheus (time-series БД) для хранения метрик
2. Развернуть и настроить Grafana для визуализации данных метрик в виде графиков и дашбордов.
3. Настроить сбор метрик с API и инфраструктуры.
4. Определить критические пороги метрик и настроить автоматические уведомления.
5. Внедрить механизмы автоматического масштабирования и балансировки нагрузки на основе метрик.
